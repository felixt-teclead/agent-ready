Fixing the PR bottleneck

Matt Pocock's three brakes for code that agents write, how agent-ready builds them into our repos, and how that compares with Superpowers.

The short version
  1. Agents multiply PRs, and human review does not scale. Matt's answer is brakes: layers that catch problems before a person has to.
  2. Three layers, cheapest first. Automated checks cost CPU, automated review costs tokens, human review costs people's time. Push each finding down.
  3. Checks lie, so design and review catch the lies. Deep modules keep tests honest. Coding standards go to a reviewer in its own context, not to the overloaded implementer. The reviewer commits fixes instead of posting comments.
  4. Human review is triaged and compounds. Door and blast radius decide how deep to look. A retro turns every repeated comment into a check or a rule.
  5. agent-ready puts these rules in the repo, where the team reviews them. Superpowers keeps them in each person's plugin. We win on owned standards, gates and governance. Superpowers wins on test rules. Both are thin on PR bodies and the retro loop.
The problem

Agents multiply the PRs. The reviewers stay the same.

In Matt's "software factory", code starts more and more of the work: a classifier turns a bug report into a fix, a slow-query report triggers a run. Every trigger adds PRs. Without brakes, the factory becomes a slop cannon, and because the codebase is the next agent's environment, bad code begets bad code.

Brake 1 · automated checks

Checks are cheap. But a green CI can lie.

Matt's agents wrote these in good faith. Each one passes, and each one proves little. Code reconstructed from the talk.

Lie 1

Tautological test

// x-post.ts
export const X_POST_CHAR_LIMIT = 280;
// x-post.test.ts
expect(X_POST_CHAR_LIMIT).toBe(280);

The test restates the code. A rename breaks it, and a wrong limit still passes.

Better: assert behaviour. A post of 281 characters is rejected.

Lie 2

Structure-sensitive test

const src = read('PitchDetail.tsx');
const a = src.indexOf('<ContentPlan');
const b = src.indexOf('<Videos');
expect(b).toBeGreaterThan(a);

It reads the source text instead of rendering the page. Any reformat breaks it.

Better: render the page and check the order the user sees.

Lie 3

Test that cannot fail

vi.stubGlobal('AudioContext', class {
  createGain() { return fakeGain; }
});
renderHook(() => useAudioBoost());

The stub removes the real AudioContext and its error modes. Those errors reach production untested.

Better: put the platform behind a seam you own, and test the seam against the real API.

Design your way out: deep modules keep tests honest

If tests may only use a small interface, they cannot couple to the internals. John Ousterhout's deep modules, in the words of Pocock's codebase-design skill:

Seam: where the interface lives. Tests go here.
Depth: behaviour a caller gets per unit of interface it must learn.
Leverage: what callers gain from depth.
Locality: change, bugs and checks stay in one place.

/improve-codebase-architecture

Scans any codebase for deepening opportunities and writes an HTML report with a before and an after for each.

Brake 2 · automated review

The implementer is overloaded. The reviewer is not.

One context window must explore, change the files and keep budget for debugging. Coding standards on top make it worse. The reviewer gets a diff and has room. "While implementation is overloaded, review is actually underloaded."

Implement makes it work. Review makes it good.

Red and green in one context window, refactor in a second one. Stop trying to one-shot good code.

Build your reviewer, do not buy it

Generic bots are too general, with false positives, or too specific, fit for one stack. Grow CODING_STANDARDS.md from your team's own mistakes. AGENTS.md stays small, with navigation pointers only.

The reviewer commits

A reviewer that comments creates work for the human. It should commit its fixes, so the human reviews a clean result. Comments only for real questions.

The loop

Review the system that writes the code, not only the code.

"Never write the same review comment twice."

What /retro proposes
  • An automated check, for a mechanical mistake. The retro skill says: build the check, full stop.
  • A CODING_STANDARDS.md rule, only for a real judgment call.
  • A navigation pointer in AGENTS.md, where the agent searched too long.
  • A cheaper tool, where a tool call burned tokens.
  • Cuts to bloated steering files and skills.
1. Layer on cheap checks. 2. Design deep modules.
3. Standards go to the reviewer. 4. Own the reviewer, let it commit.
5. Write PRs for humans. 6. Run a retro on your reviews.
Comparison

Superpowers disciplines one session. agent-ready puts the team's rules in the repo.

Superpowers v6.4.2

  • Flow: brainstorm, plan, one sub-agent per task, review, finish the branch.
  • The process lives in the plugin, in each person's home directory. A session-start hook loads it.
  • Reviewers check a generic list that ships with the plugin. No repo standards file.
  • Specs and plans are dated markdown files. Implementers run one after another.
Strongest at: test discipline inside one session.

Pocock's skills + agent-ready

  • Flow: grill the idea, spec, tickets, implement test-first, review, PR.
  • Rules, standards, domain words and gates live in the repo. A human merges every change to them.
  • The reviewer reads the team's own docs/CODING_STANDARDS.md.
  • Specs become issues. Agents take ready-for-agent tickets with nobody watching.
Strongest at: team-owned rules and many agents in parallel.

A. Adoption

highThe repo fails its own scan

AGENTS.md carries the steering rule that routing-table.md lists under Old files. Its ### Domain docs line differs from the template and points at CONTEXT.md, which does not exist, a dead pointer by pointers.md. ADR 0001 says the rule is "written twice", in CLAUDE.md and a CI guard, and that "the guard prints its enforcement status on every run"; #42 deleted that guard. .agents/skills/ holds older, diverged copies of comment-cleanup and orchestrate-comment-write plus a comment-write skill the plugin does not ship, and docs/CODING_STANDARDS.md points there. The plugin is not installed on this machine, so its merge hook does not guard this repo; .claude/settings.json denies only gh api merges.
Fix: run the scan on this repo, fix or record each finding in .agents/deviations.md, and supersede ADR 0001. Coworkers open this repo first.

highAuto-update repeats the Superpowers problem

The README says "every merge to main ships". A hook or skill change then reaches every installed repo with no diff in that repo. That is the argument the deck makes against Superpowers.
Fix: ship tagged releases with a changelog and pin the marketplace entry to a tag, or recommend the copies channel, where /update-codebase-for-agents opens a PR, for team repos.

highNo outcome numbers

The scan's three numbers measure doc hygiene, not the bottleneck. TRADEOFFS.md lists migration and comment-pass cost as "Not measured yet". Leads will ask for both.
Fix: baseline one pilot repo before and after: median time to merge, human review comments per PR, share of PRs merged without a human, repeated comments. gh gives the first three.

mediumOwnership and bus factor

A private repo on a personal Free account (ADR 0001: "ownership beat enforcement"). Every coworker needs read access by hand. All 41 commits come from two git identities in seven days, and names still move: one tier was renamed hours after it got its name. A company-wide method that ships from one personal account breaks in every repo if that account goes.
Fix: decide where the company copy lives before rollout, and freeze a v1.

mediumStubborn tier drifts silently

The override denies Superpowers skills by name. A rename upstream disables a deny rule without an error, and Superpowers updates arrive without notice, so nobody knows when the manual smoke run is due. v6.0 already merged the two reviewers into one.
Fix: record the smoke-tested Superpowers version in docs/agents/superpowers.md; a SessionStart hook warns when the installed version differs.

lowThe vocabulary is the product's, not the listener's

Routing table, fixed rows, gap list, confirmed steps, held files, rule queue, phase, worklist, Stubborn, deviations. /what-to-do needs a glossary to explain them.
Fix: pitch in Matt's terms, as the deck does, plus one page "what changes in my day": three commands.

B. The approach

highBrake 1 is not deterministic

Setup writes a check command but nothing wires it into CI or a pre-commit hook (no CI, workflow or pre-commit in plugins/agent-ready/). Agents run it because a line tells them to; humans may not run it at all. Pocock's retro calls a repo without such a guardrail "itself a finding".
Fix: setup offers a CI job that runs check on every PR, and optionally a pre-commit hook (Pocock ships setup-pre-commit). The cleanup merge rule already requires the remote's required checks; make them exist.

highNo retro loop for human review

Human review comments never flow back. Today the loop is setup question D, once; the comment pass rule queue, for comments only; and CONTEXT.md growth. That misses Matt's main multiplier. Pocock's retro is labelled "STUB: design notes only".
Fix: reuse two patterns the plugin already has. A reminder hook, like the architecture review, offers /retro over the last week's PR review threads. Its output takes existing routes: a mechanical finding becomes a lint rule or test, a judgment call becomes a CODING_STANDARDS.md line in a human-merged steering PR.

highNothing catches lying tests

Superpowers' writing-good-tests.md is sharper than anything we ship. By Matt's own logic, test rules in tdd sit in the overloaded implementer. The review side has no test rules, and /code-review's smell baseline covers none of the three lies.
Fix: give each lie its cheapest enforcer. Structure-sensitive: a lint rule that bans reading src/ files from tests. Cannot fail: mutation testing on changed files in CI, which kills over-mocked tests but not tautological ones. Tautological: a Tests section in the CODING_STANDARDS.md template, wording borrowed from Superpowers with credit.

mediumThe code reviewer reports; the overloaded implementer fixes

Only comment-review commits. /code-review reports, and /implement fixes the findings in its own full context, the pattern Matt argues against.
Fix: a review-fix sub-agent commits behaviour-preserving fixes under the same gate style as comment-review: check green, no test file touched, unresolved findings into the PR body. Pocock's in-progress implement-spec moves this way.

mediumThe gate trusts the agent

The push hook reads .git/comment-review-ok. An agent blocked by the hook can write git rev-parse HEAD into it without a review. /code-review has no gate at all.
Fix: make the stamp carry a hash of the review report, and let CI check that the PR body has the ## Comment review section for the head commit.

mediumRe-review cost after a small fix

Any commit clears the stamp, and the scope is the whole branch diff from the merge base. A one-line fix after review dispatches one Opus writer per file on the branch again.
Fix: keep the last stamped commit and scope a re-run to files changed since then.

mediumPR bodies lack merge danger

afk-handback.md has goal, decisions, not done, verification, least sure. No door, no blast radius, no visual summary. So feature PRs all get the same review depth.
Fix: add a Merge danger section to the template now, a steering diff; switch to /pr when it graduates. Later, a team decision: widen agent self-merge to two-way, localized PRs with green checks.

lowThe migration itself is a bottleneck PR

Full migration ends in one steering PR over many files (175 docs in scope on the trial repo). Approvals during the run help, but a reviewer who was not in the session faces the whole diff.
Fix: give that PR a merge-danger line and a routing summary diagram; recommend Blocks mode for teams with several reviewers.

lowComment pass churn

About 230 agent-merged PRs on the trial repo rewrite comments across the codebase. That buries git blame.
Fix: list comment-pass commits in .git-blame-ignore-revs, which GitHub honours, and measure 10 files before cleanup_comments defaults to on.
